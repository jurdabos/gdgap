# ADR 0004: Benchmark protocol — warm-only matrix, frozen query catalogue, evidence contract

- Status: accepted
- Date: 2026-08-03

## Context

Phase E must produce auditable timings, plans, result hashes, and storage costs over the implemented matrix (backends `ducklake|innodb`, variants `blind|aware`, families `q_agn|q_eq`), and the runbook requires the query catalogue and cache protocol to be frozen in an ADR before the harness is coded. Cold-cache methods are risky here: `drop_caches` changes global WSL VM state, needs privilege, and does not clear the InnoDB buffer pool. The engines are also architecturally asymmetric — DuckDB runs in-process while MySQL is a client/server service — which restricts causal claims regardless of protocol.

## Decision

- Matrix and invocation: one `gdgap bench` invocation runs one cell — `--backend ducklake|innodb`, `--variant blind|aware`, `--temperature warm` (the only accepted value), `--repetitions` ≥ 1 with default 5 (evidence runs use ≥ 5). Dataset is `nhts2017`. Every result row persists the concrete cell values; nothing is pooled across cells.
- Query catalogue (frozen): `sql/bench/` holds exactly `q_agn_01_care_trip_share_total`, `q_agn_02_mode_share`, `q_eq_01_care_trip_share_by_sex`, and `q_eq_02_ppr`. Bodies are backend-neutral and reference all relations through the `{schema}` placeholder, which the runner resolves to `lake.<variant>` (DuckLake) or `gdgap_<variant>` (InnoDB) by plain string replacement — no duplicated per-backend query texts. `q_agn` queries read only the fact grain (identical across variants) and must return equivalent values on blind and aware; `q_eq` queries read the deployed aware equity views, so the n ≥ 30 small-cell suppression (R9) stays inside the measured schema. Catalogue changes require a new ADR and re-running affected cells.
- Capability states: `q_eq` on the blind variant is recorded once per query with outcome `not_representable` and an explanatory reason — never executed, never timed, never a fabricated NULL result (R2 contrast, R11 honesty).
- Warm protocol per cell: open one fresh backend connection; for each runnable query execute one unrecorded warm-up that doubles as plan capture; then execute the recorded repetitions with the query order shuffled per repetition round by `random.Random(seed)` — the seed is user-supplied or generated, and always persisted in `envinfo.json`. Timing is wall-clock `time.perf_counter_ns` around execute-plus-full-fetch, reported in milliseconds with 3 decimals. Per-query failures are recorded (`outcome=error`, `failure_reason`) and the run continues.
- Result hash: each cell is canonicalised (`None` → `NULL`; `float`/`Decimal` → `%.9g`; otherwise `str`), cells joined with the unit separator `\x1f`, rows sorted lexicographically, and the joined text SHA-256-hashed. Hash equality is required within one engine (across repetitions, and across variants for `q_agn`). Across engines, agreement is assessed numerically with a documented float-summation tolerance — differing summation orders make byte-identical hashes an unreasonable cross-engine criterion.
- Declared controls: DuckDB gets `SET threads = 4` and `SET memory_limit = '8GB'`; the actual values are read back via `current_setting()` and persisted. Profiling (`PRAGMA enable_profiling = 'json'`) is active only during the warm-up plan capture, so recorded repetitions run uninstrumented. For InnoDB no false common setting is invented: `threads` and `memory_limit_bytes` stay empty in `runs.csv`, while `envinfo.json` records the server version and `innodb_buffer_pool_size` as backend-native settings.
- Plans: `results/plans/<backend>_<variant>_<query_id>_<temperature>_0.json`, repetition `0` denoting the warm-up. Formats are tagged and not interchangeable: `duckdb-profile-json` is a runtime profile; `mysql-explain-json` (`EXPLAIN FORMAT=JSON`) is an optimizer estimate.
- Evidence files: `results/bench/runs.csv` is the append-only raw record with the full column list from the runbook (run identity, git commit, matrix cell, outcome, timing, rows, hash, plan path, engine/python versions, controls, image digest, kernel, CPU model, RAM). `results/bench/envinfo.json` maps `run_id` to the full environment snapshot including the seed. `results/bench/summary.csv` is a derived artefact regenerated from all retained raw runs: n, median, IQR (inclusive-method quantiles), min/max, and hash stability per cell and query. `results/bench/storage.csv` is append-only.
- Storage accounting: DuckLake bytes come from the attached metadata catalog (`__ducklake_metadata_lake`), summing `ducklake_data_file.file_size_bytes` for files, tables, and schemas whose `end_snapshot IS NULL` — never from a recursive Parquet glob, which would count files retained from superseded snapshots. Tables whose small writes were data-inlined into the metadata catalog (e.g. the aware code list and reserve-code map) carry no data files and are reported with zero bytes; that catalog-resident footprint is negligible at thesis scale, and `ducklake_flush_inlined_data` is the explicit maintenance step when file parity is wanted (the fixture tests use it, since fixture-scale writes are inlined wholesale). InnoDB bytes are `DATA_LENGTH + INDEX_LENGTH` from `information_schema.tables` after an explicit `ANALYZE TABLE` refresh; per-column parity with Parquet footers is not claimed. Each measurement emits per-table rows, per-variant `TOTAL` rows, and the `aware_minus_blind` delta when both variants are measurable, with the method recorded per row.
- Cold runs are deferred: a cold path requires a validated per-engine reset procedure recorded in its own ADR; warm and cold results are never pooled. CI may smoke-test the runner on fixtures but never produces thesis timings.

## Consequences

- Four invocations cover the declared matrix; any later convenience orchestration (`--matrix full`) must expand into these cells and persist concrete values per row.
- The in-process versus client/server asymmetry remains an execution-architecture confound; it is recorded as a limitation and constrains row-versus-column causal claims in ch. 4/5 prose.
- The frozen catalogue makes result rows comparable across commits: every row carries `git_commit`, so protocol drift is detectable, and any change to queries, controls, or hashing invalidates comparability by construction and demands a new ADR.
